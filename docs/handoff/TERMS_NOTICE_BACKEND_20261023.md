## 3. 공지 종류·공개 대상·표시 방식의 구분

아래 `GENERAL`·`SERVICE`·`TERMS`는 **새 계약 제안 식별자**다. 현재 API가 이미 지원한다는 뜻이 아니다. 기존 `notice_type`의 값·사용처·원장 의미를 먼저 조사해 재사용 여부를 결정한다. 별도 의미의 필드가 필요하면 변경 이유와 마이그레이션 영향을 회신한다.

| 제안 유형 | 용도 | 기본 표시·처리 |
| --- | --- | --- |
| `GENERAL` | 일반 이용 안내 | 허용된 대상의 공지 목록·상세. 기본 팝업 없음 |
| `SERVICE` | 점검·장애·중요 서비스 안내 | 대상 공지 목록·상세. 배너·팝업·별도 발송이 필요하면 표시 정책과 발송 권한을 따로 승인 |
| `TERMS` | 약관 변경 안내 | 승인된 공지 상세와 변경 전후 원문을 고정 주소로 제공. 승인된 대상에게 공통 메일 연결 |

다음 항목은 서로 다른 설정이다.

- 공지 종류: 내용의 목적.
- 게시 대상: 전체·내부·딜러·고객 및 기존 조직 범위.
- 게시 상태·기간: 작성 중/게시/중지, 공개 시작·종료.
- 상단 고정: 목록 내 순서.
- 노출 정책: 목록, 배너, 선택적 팝업 등. **이번 기본값은 목록이며 팝업이 구현됐다고 표시하지 않는다.**
- 발송 채널: 이메일·PUSH 등. 게시 버튼을 누르는 것만으로 모든 채널을 발송하지 않는다.
- 익명 공개 여부: 로그인하지 않은 이용자에게도 본문을 공개할 수 있는지. **기존 대상 `ALL`은 익명 공개 승인을 뜻하지 않는다.**

휴면 전환 사전 안내는 **개인 계정 대상 안내**다. 사용자 확정 기준은 미접속 90일이며, 마지막 성공 로그인·전환 예정일·사용자 ID를 공개 공지 목록에 올리지 않는다. 사전 발송 시점·횟수는 별도 정책이고 임의의 7일/30일을 만들지 않는다.

현재 모바일의 ‘공지사항/마케팅 알림’ 설정은 실제 API에 연결되지 않은 항목이다. 이를 약관·계정 안내의 일괄 수신 거부 기준으로 재사용하지 않는다. 안내 목적·광고성 분류·대상·수신 옵션은 승인된 운영·법무 정책에 따라 분리한다.

이용자: 공지 목록 또는 약관 안내 메일 → 고정 공지 상세 → 변경 전/후 약관 원문
서버: 게시 성공 사건 → 승인 대상·언어 확정 → 공통 메일 발송·결과 이력

1. 기존 관리자 공지 CRUD·동시 수정 충돌 검사를 재사용한다. 약관 고지에 필요한 공지 종류·약관 연결·공개 승인 정보를 확장한다.
2. 공지에는 안정적인 게시물 ID를 부여한다. 화면을 새로 열거나 링크를 재사용해도 같은 게시물을 조회해야 하며, 메일에 제목 검색 결과나 최신 공지로 바뀌는 주소를 넣지 않는다.
3. 약관 공지 상세에는 약관명, 안내일, 시행일, 승인된 변경 요약/본문, 변경 전·후 원문 링크와 문의 안내를 제공한다. 내부 버전 문자열을 이용자 화면에 노출할 필요는 없다.
4. 이미 발송된 공지·연결 원문의 의미가 새 내용으로 조용히 바뀌지 않게 한다. 수정·정정·철회는 승인과 이력을 남기고, 기존 링크의 보존/정정 표시 정책을 확정한다.
5. 공지 열람·닫기·메일 수신을 약관 동의로 저장하지 않는다. 재동의나 미동의 시 업무 차단을 이번 작업에서 새로 추가하지 않는다. 그런 변경이 필요하면 기존 사용자 확정 범위와 별도로 승인받는다.

‘새 게시판’의 댓글·첨부 업로드·답변·검색 고도화·모든 공지 팝업·독립 모바일 관리 화면은 이번 최소 범위가 아니다.

## 5. 공개 열람과 약관 시행의 분리

### 약관 공지의 고정 상세 주소

- 익명 공개는 **승인된 `TERMS` 공지 중 명시적으로 공개 허용된 게시물만** 대상으로 한다.
- 로그인용 URL 또는 기존 조직 공지 API 전체를 `permitAll`로 풀지 않는다. 일반/조직 대상 공지와 개인정보는 기존 인증·인가를 유지한다.
- 존재하지 않는 ID, 초안, 미승인, 비공개·조직 전용 게시물은 공개 주소에서 노출하지 않는다. ID를 바꿔 다른 대상 공지를 열 수 없어야 한다.
- 고정 공개 주소에는 사용자 토큰·임시 비밀번호·인증번호·서명되지 않은 권한 상승용 파라미터를 넣지 않는다. 언어 변경은 같은 공지의 표시 언어만 바꾼다.
- 새로고침·직접 URL 진입·로그아웃·모바일 브라우저에서도 허용된 약관 공지를 읽을 수 있어야 한다. 프론트의 관리자 화면 JS나 로그인 세션에 의존하지 않는다.
- 오래된 약관 공지·원문의 보존과 열람 기간은 명시한다. 기존 1개월 목록 조건을 이유로 이미 발송한 고정 상세 링크까지 끊지 않는다. 종료·철회 이후의 설명/원문 보존은 승인된 정책에 따라 처리한다.

### 승인된 개정 원문의 사전 열람

현재 약관 조회 조건은 `PUBLISHED`, `published_at <= 조회 시각`, `effective_at <= 조회 시각`이다. 따라서 시행 전 고지 메일에서 개정 원문을 기존 ‘현재 시행 약관’ 조회로만 연결하면 열리지 않을 수 있다.

- **공개 승인**과 **현재 시행**을 구분한다. 승인·게시된 개정 원문을 사전에 읽을 수 있는 제한된 읽기 계약을 추가하거나, 동일한 승인 원문을 고정 게시 문서로 제공한다.
- 초안·미승인 약관을 공개하는 방식으로 해결하지 않는다. 기존 가입/현재 약관 조회에서 미래 시행 버전이 현재 약관으로 선택되도록 조건을 일괄 제거하지 않는다.
- 변경 전·후 원문은 각각 정확한 약관 코드·개정 식별자에 연결한다. ‘최신 약관’으로 리다이렉트해 과거 공지의 비교 대상을 바꾸지 않는다.
- 동일 코드·버전 내 실제 제공 가능한 언어를 검증한다. 없는 번역을 있는 것처럼 표시하지 않으며 실제 서버의 언어 선택/대체 계약을 프론트와 맞춘다.
- 공지 게시 기간, 사전 열람 시작, 실제 시행 시각과 사업 시간대를 구분한다. 날짜의 클라이언트 시간대 해석으로 시행 여부를 결정하지 않는다.

## 6. 메일 표시 계약과 내부 연결값

### 약관 변경 메일의 표시 필드

| 필드 | 공급 책임·표시 |
| --- | --- |
| `displayName` | 서버가 확인한 수신 계정 표시 이름 |
| `termsTitle` | 승인된 대상 약관명 |
| `noticeDate` | 확정 안내일 |
| `effectiveDate` | 확정 시행일 |
| `changeSummary` | 승인된 주요 변경 요약. HTML을 임의 실행하지 않음 |
| `noticeUrl` | 동일 공지의 고정 HTTPS 상세 주소. 변경 전후 원문은 상세에서 연결 |
| `logoUrl`, `supportEmail`, `year` | 기존 공통 메일 설정·서버 기준 값 |

언어·등록 수신 이메일은 서버가 확정한다. 웹·모바일 화면이 임의 이메일, HTML 본문, 휴면 상태나 약관 승인 여부를 정해 발송하지 않는다. 위 표는 **새 표시 계약**이며 현재 서버 DTO가 이미 이 형태로 연결됐다는 주장이 아니다.

### 표시하지 않아도 보존할 내부 정보

- 안정적인 `noticeId` 및 게시/정정 사건 식별자.
- 약관 항목 식별자와 변경 전·후 개정 식별자/버전.
- 승인자·게시자·게시 시각·시행 시각과 시간대.
- 대상·공개 승인 범위·발송 언어·수신 계정·발송 결과.

메일에 `v1`, `v2` 같은 내부 버전명을 빼더라도 위 정보는 이력·정확한 원문 연결·동일 사건 중복 방지를 위해 필요하다.

## 7. 백엔드 작업 지시

1. 최신 백엔드 작업본에서 기존 공지 `Service/Repository/Mapper`, 약관 조회, 공통 메일 렌더러·발송기·원장/스케줄을 먼저 조사한다. 동일 기능이 추가돼 있으면 재사용하고 차이만 보완한다.
2. 기존 공지 저장 입력·원장의 대상/기간/상태/상단 고정과 원본 `noticeType`을 보존한다. 신규 종류·약관 연결·익명 공개 승인의 저장 방식과 기존 데이터 처리 방안을 확정한다. NULL이나 과거 값을 임의로 `TERMS`/공개로 추정하지 않는다.
3. 관리자만 허용된 대상·유형을 작성/게시할 수 있게 검증한다. 기존 `expectedModifiedAt` 동시 수정 검사를 유지하고, 게시 직전 필수 본문·원문 링크·날짜·공개 승인·언어를 다시 검사한다.
4. 고정 공지 상세 조회와 승인된 개정 원문 사전 열람을 구현한다. 실제 method/path/요청/응답/오류를 프론트에 회신한다. 이 문서의 GitHub 주소나 예시 ID를 운영 API 경로/데이터로 하드코딩하지 않는다.
5. 게시 성공 후에만 발송 사건을 생성한다. 승인된 등록 수신자·대상·언어·공지 URL을 서버에서 선택한다. 제목·본문·링크의 출처를 검증하고 기존 escape/치환·URL 허용 정책을 유지한다.
6. **약관 항목 ID + 개정 ID + 공지 게시/정정 사건 + 수신 계정 ID + 메일 종류** 기준으로 중복을 방지한다. 웹과 모바일에서 같은 사건을 요청해도 중복 발송하지 않는다. 서로 다른 약관의 같은 `v2`를 같은 사건으로 취급하지 않는다. 재시도는 최초 사건·언어·승인 원문을 유지한다.
7. 기존 발송 이력·outbox·재시도 경계를 재사용한다. 발송 접수, 제공자 수락, 실제 도착, 실패, 결과 불명확을 구분하고 결과 불명확 상태에서 새 사건을 무조건 만들지 않는다. 실제 수신자·비밀값을 로그나 공개 페이지에 노출하지 않는다.
8. 일반/불리한 약관 변경의 안내 기한·대상·채널·문의/거부 절차는 승인된 현행 약관과 법무·업무 정책에 맞춘다. 시안 날짜를 운영 기본값으로 삼거나 임의의 고지 일수를 확정하지 않는다.
9. 게시만으로 로그인 팝업·PUSH·전원 메일을 자동 추가하지 않는다. 팝업이 추후 승인되면 노출 대상·빈도·기간·오늘 숨김/닫기/읽음의 보관 범위를 별도 계약으로 정의한다. 전체 조회수를 개인별 읽음 증명으로 재사용하지 않는다.
10. 실제 SES/SMTP·도메인·자격은 기존 승인된 서버 설정을 사용한다. 프론트 `VITE` 변수나 문서/Git에 키를 넣지 않는다. 이번 시안 전달을 근거로 실제 계정·DB·발송 설정을 변경하거나 고객에게 시험 발송하지 않는다.

## 8. 프론트 동반 작업 — 백엔드만으로 끝나지 않는 항목

| 담당 | 필요한 작업 | 현재 상태와 경계 |
| --- | --- | --- |
| 어드민 | 기존 공지 등록/수정에 확정된 유형·약관 연결·공개 승인·게시 정보 표시 및 검증 추가 | 현재 저장 계약에는 해당 구분이 없음. 별도 게시판을 복제하지 않음 |
| 플릿 웹 | 허용된 공지 목록·상세 진입점, 유형 표시, 고정 상세 주소 직접 진입/새로고침 처리 | API 연결기 존재와 사용자 화면 연결 완료를 구분 |
| 공통 공개 읽기 화면 | 메일의 `noticeUrl` → 승인된 약관 공지 → 정확한 변경 전후 원문 | GitHub 시안과 실제 API 연결은 별도. 공개 페이지에 관리자/조직 공지 데이터 혼합 금지 |
| 모바일 웹 | 기존 알림 내 공지 목록/상세 유지, 새 계약의 유형·고정 주소 연결, 외부 메일 링크 수신 화면 확인 | 로그인 자동 팝업으로 바꾸지 않음. 별도 모바일 메일 템플릿/발송기 추가 금지 |
| 공통 메일 | 내부 버전 표시 제거, `noticeUrl` 한 개로 연결, 기존 로고·헤더·라운드·언어·변수 보호 | 표시 시안 변경과 실제 Java 템플릿 소비·발송 완료를 분리 |

새 필드·공개 열람 API·언어/날짜 응답이 회신되면 각 앱의 기존 전송기와 응답 검증을 함께 맞춘다. 백엔드에서만 필드를 추가한 상태를 화면 적용 완료로 보고하지 않는다. 모바일 앱 소스와 AWS 실제 프론트는 이번 GitHub 시안 게시 범위에 포함하지 않는다.

실제 환경 통합·수신함 테스트는 승인된 개발 계정/수신 주소와 허가된 범위에서만 수행한다. 화면 시안·정적 파일 검증만으로 위 서버 완료 조건을 통과했다고 보고하지 않는다.
