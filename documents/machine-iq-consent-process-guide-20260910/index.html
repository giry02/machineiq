실선 화살표

업무가 진행되는 주 경로입니다. 왼쪽 단계의 처리 결과가 오른쪽 단계의 입력으로 넘어갑니다.

회색 점선

공정 이동이 아니라 해당 단계의 데이터 정의를 연결합니다. 점선 끝의 표는 화면이나 API의 다음 단계가 아닙니다.

논리명

업무 담당자가 이해하는 데이터 이름입니다. 예: 차량, 단말, 동의 상태, 승인 요청.

물리명

API·DB에서 구현 시 사용하는 후보 필드명입니다. 실제 확정 명세와 다르면 연계 설계 단계에서 조정합니다.

세 가지 관계를 구분해야 합니다

① 차량–단말 관계는 “어떤 단말이 어떤 차량에 장착됐는가”, ② 고객·딜러–차량 관계는 “어느 고객이 소유하고 어느 딜러가 판매·서비스하는가”, ③ 동의·승인 관계는 “고객 동의와 딜러 승인을 거쳐 어느 계정에 차량 조회 권한을 줄 것인가”를 의미합니다. 원본에는 동의 만료기간이나 기간별 권한 규칙이 정의되어 있지 않습니다.

전체 01

전체 공정: 생산에서 화면 조회와 서비스 처리까지

세부 공정이 어느 위치에 속하는지 먼저 설명하는 상위 지도입니다. 최초 매핑·상시 수집·동의 관계 갱신·화면 조회를 분리하고, FigJam의 A01~A20 단계와 같은 순서로 설명합니다.

① 생산·추적성 등록 · PPT 확인MES/MQS에서 차량·단말 바코드를 등록하고 SAP 추적성 정보에 PP와 Terminal No를 연결
② 최초 활성화·미동의 매핑 · PPT 확인Agent가 단말 상태를 판정하고 미동의 API를 호출하면 Cloud가 EAI로 차량 후보를 조회
③ 상시 운행 데이터 수집 · 기존 코드 확인Agent가 /collector/v1/equipment/*로 전송하고, Collector가 차량 귀속 정보를 보강해 운영·이벤트 DB에 적재
④ Web/App 동의·차량 승인 · PPT 확인회원가입에서 정보제공 동의를 받고 계정·장비 승인 후 동의 EAI로 고객·차량·딜러 관계를 갱신
⑤ 화면 조회 · 기존 코드 확인Web/App이 /fleet/... API를 호출하면 Backend가 허용 차량 범위를 적용하고 저장된 DB를 조회
이 장에서 강조할 핵심

미동의·동의 EAI는 매 운행 데이터가 들어올 때 호출하는 경로가 아닙니다. 미동의 EAI는 단말 활성화·최초 매핑과 실패 재처리, 동의 EAI는 Web/App 동의·차량 승인 뒤 관계 갱신에 사용합니다. 평상시 텔레메트리는 별도 수집 경로입니다.

세부 02

NEW 단말–차량 자동 매핑

생산 바코드와 단말 바코드가 연결되고, 단말의 최초 통신을 기준으로 MIQ에 차량–단말 관계가 생성되는 경로입니다.

02-01
생산 바코드 스캔
차량 바코드와 단말 바코드를 함께 식별합니다.
02-02
추적성 부품 등록
생산오더와 단말 번호를 SAP 추적성 정보로 연결합니다.
02-03
Terminal Activated
차종별 시점에 단말이 활성화되고 Agent가 최초 상태를 확인합니다.
02-04
Agent 상태 판정
통신·장착·GPS·배터리의 O/X/NULL을 Agent가 판정합니다.
02-05
미동의 API 호출
Agent가 Cloud에 Terminal ID와 판정 결과를 전송합니다.
02-06
MES EAI 호출
Cloud가 Terminal SN으로 PP·Equipment 매핑을 조회합니다.
02-D1
Equipment ID 존재?
추적성 부품 등록 여부에 따라 Positive 또는 Negative로 응답합니다.
02-07
차량–단말 매핑 저장
성공 시 Cloud에 관계를 저장하고 해당 Terminal ID의 미동의 API 재호출을 종료합니다.
Positive Response

Equipment ID가 확인되면 차량–단말 매핑을 저장하고, PPT 27장 기준으로 해당 Terminal ID의 미동의 API 재호출을 중단합니다.

Negative Response

매핑이 없거나 MES DB 저장이 실패하면 일정기간 후 재호출합니다. PPT에는 1시간 간격, Daily Batch 5회·30회, Count 3·5가 혼재하므로 운영 기준 확정이 필요합니다.

세부 03

TO-BE 미동의 EAI: 동의 전 차량 기본정보 매핑

단말 활성화 시 Agent가 호출한 미동의 API를 Cloud가 받아, Terminal No 기준의 추적성 정보를 조회하고 개인정보 제공 동의 전 허용된 정보만 저장하는 공정입니다.

03-01
Agent 미동의 API
Terminal Activated 시 Terminal ID와 상태 판정값을 Cloud에 보냅니다.
03-02
Cloud Terminal ID 저장
수신한 Terminal ID와 호출 결과를 저장하고 미동의 EAI를 요청합니다.
03-03
미동의 EAI 호출
Terminal_No, Agree=X로 DIPP_SEND_EQUIP_DIV_TMS를 호출합니다.
03-04
SAP/MES 추적성 조회
Terminal No와 연결된 Equipment ID 및 제공 가능한 차량 기본정보를 조회합니다.
03-D1
매핑 정보 존재?
Terminal–Equipment 매핑이 있는지 확인합니다.
03-05
제한 기본정보 저장
동의 전 허용 항목과 차량–단말 매핑을 Cloud DB에 저장합니다.
03-06
Agent 응답
성공 시 Equipment ID를 반환하고, 실패 시 NULL/Negative로 재시도 대상임을 알립니다.
Y · 매핑 정보 존재

PKMT, 모델, F_BATT, 영업·서비스 딜러, 보증개시일, 고객고유번호를 저장합니다. 차대번호와 고객 연락처는 동의 전 제공하지 않습니다.

N · 매핑 정보 없음

추적성 부품 미등록으로 기록하고 배치·재호출 대상으로 둡니다. 횟수 임계 초과 시 관리자 Alert와 생산팀 확인 절차로 넘깁니다.

  1. ‘미동의’는 사용자가 화면에서 거절 버튼을 누른 오류 상태가 아니라, 고객의 명시적 정보제공 동의 전 호출하는 인터페이스 구분입니다.
  2. Agent는 Web 화면의 사용자 권한을 판단하지 않습니다. 활성화된 단말의 Terminal ID와 상태값을 Cloud에 전달합니다.
  3. Cloud는 이 최초 매핑·재처리 시점에만 EAI/SAP/MES 추적성 조회를 수행합니다.
  4. 성공하면 Equipment ID와 제한 기본정보를 저장하고 같은 Terminal ID의 반복 호출을 멈춥니다.
  5. 실패한 요청만 일정기간 후 재호출하며, 정상 텔레메트리 수집은 이 경로와 분리합니다.

세부 05

가입·승인·수동 보완

자동 매핑만으로 해결되지 않는 계정 생성, 고객 동의, 딜러 승인, 장비 식별 보완을 처리하는 보조 공정입니다.

A. 회원가입 및 자동 승인

  • 고객이 사업자번호·연락처와 선택적으로 차량호기를 입력합니다.
  • Web DB–신규 EAI–SAP 영업모듈에서 사업자번호와 고객·차량 정합성을 확인합니다.
  • 차량호기를 입력한 경우 SAP 생산모듈에서 Terminal ID를 확인합니다.
  • 사업자번호와 차량번호가 모두 일치할 때 자동 승인하고, 나머지는 승인 대기로 전환합니다.

B. 고객 동의 및 차량 승인

  • 소유자 계정과 처리 딜러를 선택하고 약관에 동의합니다.
  • 차량 권한 신청 후 딜러 승인 완료 여부를 확인합니다.
  • 승인 시 고객번호와 승인 차량을 연결하고 고객번호 일치 차량에 동의 EAI를 호출합니다.

C. 수동 매핑 보완

  • Equipment ID가 불명확하면 단말 시리얼 사진 등 증빙을 접수합니다.
  • 운영자가 SAP/MES/MIQ 기준정보를 대조해 실제 장비와 단말 일치 여부를 확인합니다.
  • 일치하면 수동 관계를 저장하고 자동 매핑 프로세스로 다시 연결합니다.

설명 시 분리할 항목

  • 가입 승인과 차량 조회 승인은 같은 승인이 아닙니다.
  • 원본은 가입 시 한 번의 동의로 고객 보유 전체 장비를 조회할 수 있도록 동의서 문구를 보완해야 한다고 명시합니다.
  • 수동 보완은 자동 공정의 예외이며 정상 경로로 설명하면 안 됩니다.

Q&A

설명 자리에서 예상되는 질문

현재 FigJam의 의미를 설명하기 위한 답변이며, 실제 운영 정책과 물리 테이블은 확정 과정에서 달라질 수 있습니다.

Q1. 차량 데이터가 들어올 때마다 MES·SAP를 다시 조회하나요?
아닙니다. MES·SAP/EAI 조회는 Terminal Activated 시의 최초 차량–단말 매핑, 실패 재처리, 고객 동의 후 관계 갱신에 사용합니다. 평상시 위치·가동·배터리·충격·에러 데이터는 Agent–Cloud의 별도 수집 경로로 저장합니다.
Q2. Agent가 고객의 동의 여부와 화면 표시 여부를 판단하나요?
PPT에서 Agent는 Terminal Activated 시 단말 상태를 판정하고 미동의 API를 호출하는 주체입니다. 고객의 정보제공 동의는 Web/App 가입 과정에서 확보하며, 화면에 보여줄 차량은 Cloud에 저장된 계정–고객–차량–딜러 관계를 기준으로 서버가 결정합니다.
Q3. “미동의 EAI”는 차량 매핑 실패를 의미하나요?
아닙니다. 미동의 EAI는 개인정보 제공 동의 전 호출하는 제한 인터페이스입니다. 이 인터페이스 안에서 추적성 매핑이 존재하면 제한 기본정보를 저장하고, 매핑이 없을 때만 Negative 응답과 재시도 경로로 갑니다.
Q4. 미동의 상태에서도 어떤 정보를 받을 수 있나요?
PPT 기준으로 PKMT, 모델, F_BATT, 영업·서비스 딜러, 보증개시일, 고객고유번호는 받을 수 있습니다. Sales Order, 차대번호, PP, 고객사업자번호, 이메일, 휴대전화, 성명은 동의 전에는 받지 않습니다.
Q5. NEW와 TO-BE는 서로 다른 최종안인가요?
서로 대체하는 버전이 아닙니다. NEW는 생산·활성화 시 차량–단말 매핑 방식을 바꾸는 공정이고, TO-BE는 그 요청을 처리하는 미동의 EAI와 Web/App 동의 후 고객·차량·딜러를 연결하는 동의 EAI의 상세 공정입니다.
Q6. 동의 EAI는 언제 호출하나요?
회원가입에서 정보제공 동의를 확보하고 계정·차량 승인 절차가 진행된 뒤 호출합니다. 다만 PPT 16장과 22장에서 딜러 차량 승인과 동의 EAI의 선후관계가 다르게 표시되어 정확한 호출 시점은 고객 확인이 필요합니다.
Q7. 자동 매핑에 실패하면 어떻게 하나요?
Negative 응답 후 일정기간 경과 시 미동의 API를 재호출하고, 배치 횟수 임계 초과 시 관리자 Alert와 생산팀 확인으로 넘깁니다. 차량 ID가 불명확한 가입 건은 명판·Terminal 사진을 받아 운영자가 수동 매핑합니다.
Q8. Agent 데이터는 MIQ에 저장되고, 화면은 어떻게 가져오나요?
기존 코드 기준으로 Agent는 /collector/v1/equipment/*로 MIQ Collector에 전송합니다. Collector는 VW_EQUIPMENT_TIME으로 차량·업체·그룹·시간대를 보강해 운영·이벤트·배터리·최신 상태 테이블에 저장합니다. Fleet·Dealer 화면은 Agent에 직접 연결하지 않고 /fleet/... Backend API를 호출하며, Backend가 허용 Equipment 범위를 적용해 해당 DB를 조회합니다.
Q9. 현재 표의 API와 DB 필드가 최종 확정인가요?
Collector 경로와 주요 적재 테이블은 기존 소스에서 확인한 현재 구조입니다. 다만 NEW/TO-BE 이후에도 같은 물리 구조를 유지할지, 동의 전 텔레메트리를 저장할지, 일·월 집계를 어떤 운영 배치가 갱신할지는 최종 설계에서 확정해야 합니다.
